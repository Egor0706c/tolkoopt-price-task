# Обновление клиентских прайсов

## Вопросы до реализации

1. **Как сопоставляются товары и предложения:** производитель + артикул, аналоги, упаковки, остатки, НДС и стоимость доставки? Это важнее скорости: ошибочное сопоставление меняет цену другого товара; без однозначного ключа предложение не попадает в расчёт.
2. **Какие ограничения на изменение цены и кто согласует исключения:** минимальная цена, максимальный скачок, допустимая давность данных? Ответ определяет, что применяем автоматически, а что оставляем на ручную проверку; правила должны быть версионируемыми.
3. Что означает «каждый час»: начало сбора или опубликованный прайс, сколько товаров и клиентов, сколько времени сейчас занимает пересчёт?
4. Как действующая система принимает Excel, поддерживает ли пакетный импорт, версии прайса и возврат к предыдущей версии?
5. Кто консультирует по сборщикам, какие у площадок ограничения доступа и кто получает уведомление о сбое?

**Допущения:** есть однозначный ключ товара; публикация готового прайса может выполняться атомарно; правила цены соответствуют `starter.py`; для автоматического пересчёта нужны свежие полные данные, при сбое сохраняется прежняя цена. Допустимую давность и пороги массовых аномалий согласуем до включения автоматического режима.

## Простая архитектура

1. Планировщик раз в час запускает сбор с уникальным `run_id`; одновременно два запуска не работают.
2. Один Python-сервис вызывает существующие сборщики примерно 20 площадок с ограниченной параллельностью, тайм-аутами и ограниченным числом повторов.
3. Сырые результаты и ошибки сохраняются неизменными файлами, а в PostgreSQL пишутся нормализованные предложения, время сбора, площадка, статус запуска и версия правил.
4. Перед расчётом проверяются сопоставление товара, обязательные поля, валюта/единицы, свежесть, полнота и аномальные изменения относительно предыдущего успешного сбора.
5. Для каждого товара пригодность данных определяется отдельно: сбой одной площадки не останавливает сбор остальных, но неполный набор не применяется автоматически и сохраняет текущую цену.
6. Повторная обработка одного `run_id` не создаёт новый прайс благодаря уникальному ключу запуска и товара, а расчёт использует сохранённый снимок предложений.
7. Функция расчёта возвращает `HOLD`, `REVIEW` или `APPLY`; только `APPLY` попадает в автоматическую публикацию, остальные решения сохраняются с причиной.
8. Готовый прайс сначала записывается как новая версия, проходит проверку количества строк и масштаба изменений, затем атомарно становится текущим через существующий импорт или переключение версии.
9. Начну с теневого режима рядом со старой системой: сравню результаты без публикации, затем включу ограниченный набор товаров и только после проверки расширю охват.
10. При проблеме выключу новую публикацию и верну последнюю рабочую версию; старая система продолжит работать, а журнал запусков и уведомления покажут причину сбоя.

## Код и проверка

Python 3.10+, внешние зависимости не нужны:

```bash
python -m unittest -v
python starter.py
```

Исправлены тайм-аут/ошибки источника, фильтрация предложений, вычисления через `Decimal`, округление вниз, минимальная цена и порог ручной проверки. Тесты проверяют обычный расчёт, сбои и тайм-аут, отсутствие подходящих предложений, границы 30%, минимум и отмену задачи. В рабочем коде дополнительно настроил бы достаточную точность Decimal для максимальных допустимых денежных сумм, согласованных со схемой данных.
